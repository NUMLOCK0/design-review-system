# 品牌协作小程序 UI 与交互规划

配套视觉稿：[PNG 预览](uniapp-redesign-v1.png) · [可编辑 SVG](uniapp-redesign-v1.svg)。本提案以现有 uni-app、聊天、邀请会话和需求协作 API 为基础，面向品牌方微信小程序。示例内容仅用于展示界面结构。

## 与 PC 端统一的配色

小程序沿用 Web 品牌方主题：主操作蓝 `#2563eb`、强调靛紫 `#4f46e5`、浅蓝底 `#eff6ff`、边框 `#bfdbfe`、页面冷蓝灰底 `#e8eff8`。工作台顶部使用 PC 品牌方仪表板的靛紫、紫色到天蓝渐变；成功和待处理状态保留绿色、琥珀色语义色。按钮、选中态、进度条、链接和图标按 PC 主题映射，表面卡片和正文对比度保持一致。

## 设计目标

- 首页直接回答“现在该做什么”，把填写、确认、审核等待办放在项目列表之前。
- 邀请会话与订单会话进入同一套会话列表和聊天工作区；业务类型显示为轻量标签，不再分成两套入口体验。
- 需求表单在聊天里发起，聊天记录、表单版本和双方确认记录互相可追溯。
- 主操作固定在底部安全区上方；长表单和聊天历史独立滚动，避免按钮被键盘或内容挤走。
- 状态同时使用文案和颜色表达，不能只靠颜色；草稿、发送中、失败、已保存都要清楚可见。

## 导航结构

建议底部保留四个主入口：**工作台、会话、设计稿、我的**。工作台展示订单项目与待办；需求表单和确认详情从对应会话进入，不额外占用一级导航。新建邀请会话使用会话页标题栏的加号，创建后立即进入新会话。

会话页采用一个列表模型，混排订单会话和邀请会话，按最近活动排序。每项保留相同的信息层级：对方/会话名、最后消息或活动、状态标签、未处理提示。类型标签用于区分“订单”或“邀请”，不改变点击行为和聊天布局。

## 核心流程

### 分享并接入会话

1. 创建者点击会话页加号，填写名称后创建；成功后直接打开聊天。
2. 创建者在未加入成员的会话内点击“分享会话”，先生成有效期为 7 天的邀请凭证，再调用微信原生好友分享面板。分享卡片标题显示会话名称，路径携带邀请凭证。
3. 接收者点卡片打开小程序。小程序先校验并保留邀请凭证；已有登录态就自动加入并进入聊天，没有登录态则先微信登录，登录成功后自动继续加入。
4. 凭证无效或过期时展示明确原因和“请创建者重新分享”；网络失败可重试，避免重新登录或重新填写。

当前服务端邀请会话只允许首位接收者加入。邀请已成功使用后，创建者的分享入口应关闭并显示成员状态，避免让用户误以为还能邀请第二人。H5 只用于页面联调，不提供微信好友原生分享能力。

### 统一会话与聊天

从订单卡片或邀请会话卡片进入同一聊天页面。页面由统一的消息时间线、输入区和工具栏组成；订单类型额外显示订单阶段、需求档案入口，邀请类型显示参与者和分享入口。消息卡片在聊天中预览，点击后打开对应的表单、确认或设计稿页面；返回聊天时恢复原滚动位置和输入草稿。

输入区交互：

- 文本在本地先保存为待发送，服务端确认后显示“已保存”；断线时显示“待发送”，持续失败时提供重试和删除待发消息。
- 图片/文件先上传并显示进度，上传成功后再发送消息；取消上传不丢失文字草稿。
- “＋”工具面板包含需求表单、上传素材、分享会话等与当前会话类型相符的动作；不可用动作隐藏或说明原因。
- 键盘弹出时工具栏可收起，输入框贴近键盘；键盘关闭后恢复完整工具栏。
- 聊天页回到前台先补拉历史消息再恢复轮询，避免出现新消息顺序错乱。

### 填写需求单

1. 从聊天工具栏或需求卡片点击“填写需求”，按“项目目标 → 视觉方向 → 素材与交付”分步填写。
2. 离开字段或输入停止后保存草稿，顶部显示“正在保存 / 已保存 / 保存失败”；保存失败时保留本机内容并允许重试。
3. 提交前展示必填项检查和完整预览。缺项时定位到第一个错误字段，不清空已填内容。
4. 提交后生成不可覆盖的表单版本，并在聊天时间线追加表单卡片。后续修改通过“发起修订”创建新版本，旧内容和确认记录保留。

### 双方确认需求

确认页突出候选版本号、来源表单、完整摘要、相对上一版的变更以及双方确认进度。用户可逐字段展开详情；“提出修改”必须写明原因，“确认需求”前显示确认版本和确认后影响。双方确认制下，第一方确认后状态变为“等待另一方”，第二方确认后正式锁定该版本。锁定后的需求只通过修订创建新候选版，不回写旧版本。

设计稿审核从工作台待办或会话中的设计稿卡片进入。先看单张大图与设计师说明，再做通过或要求修改；要求修改需要标注对象和说明，完成后将结果写回对应会话。

## 页面状态与反馈

| 场景 | 页面反馈 | 可执行动作 |
| --- | --- | --- |
| 首屏加载 | 骨架屏保留页面结构 | 下拉刷新、失败重试 |
| 空会话 | 解释如何创建或加入 | 创建会话、从分享卡片加入 |
| 邀请待加入 | 显示等待状态及有效期 | 重新生成分享凭证 |
| 草稿保存中 | 字段附近或顶部轻提示 | 继续填写 |
| 消息断网待发 | 消息显示待发送标记 | 自动重试、手动重试、删除 |
| 确认被他人更新 | 提示版本已变化并刷新差异 | 查看最新版本后再确认 |
| 邀请过期/已被加入 | 说明凭证状态，不展示空白页 | 联系创建者重新邀请或进入已有会话 |

## 数据和接口配套

当前项目已有登录、邀请加入、会话消息、表单填写、候选版本和确认接口，可支撑主流程。视觉稿中“未读数量”需要服务端维护每位成员的已读游标或会话已读状态；实现前先隐藏未读数字，避免用消息数或更新时间冒充未读。列表排序可先用现有 `updatedAt / lastMessageAt`，后续由会话聚合接口统一返回类型、最后活动、参与者、状态与未读计数，避免前端并发拼接多套数据。

建议的统一会话列表返回字段：`id`、`kind`（order/intake）、`title`、`counterpart`、`lastMessage`、`lastActivityAt`、`status`、`unreadCount`、`pendingAction`。发送与确认继续沿用幂等键、版本号和服务端权限校验；小程序不持有微信 AppSecret。

## 落地顺序

1. 建立小程序视觉基础和底部导航：颜色、字号、间距、按钮、输入框、状态标签、空态与加载态。
2. 优先完成会话列表、统一聊天页、分享卡片接入和登录后续接，先验证最核心的拉新与沟通链路。
3. 再整理表单分步填写、草稿状态、提交预览、需求差异与双方确认页。
4. 最后统一工作台待办和设计稿审核入口，并在微信开发者工具与真机上验证分享、键盘、安全区、附件上传和网络中断恢复。

此稿是 UI/交互提案，尚未改动现有页面实现。确认视觉方向后，可按上述顺序落到 `apps/uni-app/src/pages` 与共享组件中。
