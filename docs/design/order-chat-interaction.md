# 订单协作沟通交互方案

参考用户提供的 `design_chat_app.html`，保留「会话列表 / 对话协作 / 视觉契约」三栏工作方式，改为当前系统的订单、品牌方和设计师角色。设计图见 [PNG](order-chat-workbench.png) 或可编辑的 [SVG](order-chat-workbench.svg)。

## 核心场景：用需求卡锁定设计范围

1. 从订单页进入该订单会话。左栏显示订单、未处理数量与最新动作；中栏以订单时间线展示文本、素材、需求卡和后续批注；右栏汇总已确认的协作记录。
2. 设计师点击底部「业务卡片」，按业务类别挑选模板。卡片选择层先展示用途和必要字段，再进入配置预览；尚未发送的编辑内容只保留为草稿。
3. 发送后，品牌方在卡片内填写尺寸、数量、视觉方向、素材、参考和截止时间。提交时校验必填项，并生成 `v1`。聊天流只展示摘要，点击卡片可展开完整内容。
4. 设计师逐项核对并选择「确认需求」或「提出修改」。提出修改时必须填写原因，品牌方据此生成 `v2`；旧版本保留，禁止直接覆盖。
5. 双方确认后，右栏生成只读快照，记录版本、参与人、时间、原始消息和附件。之后的加急、增项、改稿与验收均以独立协作卡挂到同一订单时间线。

## 关键状态与反馈

| 对象 | 状态 | 页面反馈 |
| --- | --- | --- |
| 普通消息 | 待发送 / 保存中 / 已保存 / 发送失败 | 待发送与失败的消息保留原文并可重试；仅服务端落库确认后显示「已保存」。没有接收方回执时不显示「已读」。 |
| 需求卡 | 草稿 / 待填写 / 待设计师确认 / 待品牌方修订 / 已确认 | 每次状态变化在聊天流产生独立事件；右栏区分待确认与已确认版本。 |
| 附件 | 本地选择 / 上传中 / 可发送 / 上传失败 | 上传成功并获得可访问的素材标识后才能随消息发送；失败时保留草稿。 |
| 连接 | 在线 / 断线重连 / 历史补齐中 | 断线不删除待发内容；恢复后按消息序号补拉并去重。 |

## 页面布局与收窄规则

- 桌面端采用约 `18% / 57% / 25%` 三栏。中栏始终保留消息输入区，右栏只展示当前订单的契约快照与案例参考。
- 窄屏先显示会话列表；进入订单后以全屏消息流为主，「协作档案」改为抽屉。需求卡保持同一字段与状态语义，不单独维护一套小程序业务逻辑。
- 快捷工具按业务频率排序：标准发单、业务卡片、沟通卡箱、图片批注、AI 风格。AI 生成内容需由人预览确认后才能发送。

## 与当前实现的关系

当前项目已实现 Socket.IO 订单聊天、数据库保存、重试去重、断线补拉，以及文字版需求核对卡、A/B 提案卡和选择记录。页面使用真实订单数据，设计图中的示例品牌和订单仅是占位内容。附件、图片批注、AI 风格、正式契约版本及导出仍属于后续开发方案；聊天卡片目前不会改变订单审核状态。
