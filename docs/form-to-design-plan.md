# 从设计表单整理设计方案：产品与技术方案

状态：方案，尚未按本文实现。依据为用户提供的两张字段流转图、当前仓库的表单与需求协作代码；未收到某个项目的实际表单答案，因此本文不包含该项目的具体视觉结论。

## 1. 目标与边界

让设计师从同一项目已提交的表单、商品图、竞品图和聊天记录中，得到一份**有来源、可编辑、可确认、可版本追溯**的设计方案。方案应回答“做什么、为什么这样做、怎么执行、还缺什么”，并作为后续人工设计或工作流的输入。

产品链路：

```text
选定项目与来源版本 → 解析和归一字段 → 展示证据与缺口 → 生成方案草稿
→ 设计师编辑与核验 → 品牌方/指定人员确认 → 冻结方案版本 → 绑定执行与审核
```

三种对象分别管理：**表单答案**是原始证据，**正式需求**是双方确认的范围与约束，**设计方案**是对该需求的创意和执行安排。生成草稿不等于需求确认、方案确认或开始生图。订单价格、支付和交付承诺继续由现有订单流程决定。

## 2. 截图中的资料与处理规则

| 来源 | 可提取内容 | 在方案中的用途 | 当前必须提示的限制 |
| --- | --- | --- | --- |
| 我的商品图，多张 | 商品主体、外观特征、使用场景；按 SKU/角度聚类 | 商品档案、主体呈现与素材清单 | 图片观察属于识别结果，需核对商品名称、材质、功效等事实；不能仅凭图片编造卖点 |
| 竞品图，多张 | 叠字母版、卖点表达方式、构图参考、可见色彩 | 参考分析与差异化方向 | 截图标注“版面结构未接入”；在接入前不得生成确定的版面结构结论。“竞品配色仅 1 色”只能当作单个样本，不能当完整色板或品牌色规范 |
| 聊天记录/评价 | 商品信息回填、卖点候选、痛点候选、客户原话、交付要求 | 目标、文案候选、风格意向、待确认项 | 截图标注“交付要求未核验”；尺寸、格式、数量、截止时间等未核验项不能写成已承诺交付规格 |
| 订单内已提交表单 | 使用场景、目标、必展元素、硬性约束、交付规格等 | 需求基线与方案约束 | 只采用明确选中的提交版本；冲突需人工解决 |

图 2 表示同一字段可供多个环节消费，例如商品档案、卖点候选、文案生成和风格推荐。实现时应维护**字段到用途的声明式映射**，而不是把图上的圆点解释成数据已经存在或结论已经核实。图中红色叉号按“缺失/不可用/待验证”处理。

### 来源优先级

1. 已确认的正式需求版本中的明确约束。
2. 被选中的已提交表单版本及品牌方明确确认的聊天内容。
3. 商品图片的可见事实和客户原话，均带原始引用。
4. 竞品分析、AI 推断和设计师建议，只能作为“分析/建议”，不能覆盖明确约束。

优先级不替代冲突处理。例如表单写“蓝色背景”、聊天写“改成白色背景”时，应列出两条来源和时间，要求选定有效要求；不能静默采用较新的消息。

## 3. 设计方案的固定结构

一份方案对应一个项目/订单和一个需求版本；可包含多个交付项，每个交付项单独列规格。建议固定以下章节：

| 章节 | 必须包含的内容 |
| --- | --- |
| 项目摘要 | 设计类型、使用平台/场景、目标、受众、方案所依据的正式需求版本 |
| 商品与受众 | 商品/SKU、可核实的外观信息、使用场景、目标用户；未知项留空 |
| 核心策略 | 主卖点与辅助卖点候选、对应证据、痛点与利益点、差异化理由 |
| 视觉方向 | 1–2 个方向的主题、气质、色彩、字体、构图与参考；将硬性要求和设计建议分开 |
| 画面/页面规划 | 主图按信息层级列主体、标题、卖点、辅助信息；详情页按楼层列主题和素材；未接入结构分析时标为待设计师制定 |
| 文案与素材 | 必须原样使用的文案、可改写文案、禁用说法、商品图/Logo/参考图及缺失素材 |
| 交付与验收 | 数量、尺寸、格式、源文件、截止时间、审核人、校验状态；无法核验的项目列待确认 |
| 风险与待确认 | 来源冲突、事实不明、单样本推断、版权或平台规范问题及负责确认人 |
| 来源索引 | 每个关键结论指向表单提交/字段、图片资产、聊天消息或人工编辑记录 |

每条内容带 `classification`：`confirmed_requirement`（已确认要求）、`source_fact`（可见或可核实资料）、`proposal`（设计建议）、`unverified`（待核验）。界面用文字标签显示，不能只靠颜色区分。

**生成示例，使用占位符而非虚构数据：**

```text
交付项：电商主图 / [平台与尺寸待确认]
目标：[来自表单的明确目标]
主卖点：[候选卖点 A]（证据：表单 X / 字段 Y；待品牌方核实）
视觉方向 A：[设计师建议的构图和色彩]（建议）
必须展示：[已确认的元素]
交付规格：[格式/数量/源文件待核验]
待确认：是否采用竞品图中观察到的单一颜色；详情页楼层结构是否由设计师重新制定。
```

## 4. 生成流程与人工关口

| 阶段 | 系统动作 | 人工动作/放行条件 |
| --- | --- | --- |
| 选择来源 | 列出表单提交版本、正式需求版本、图片与聊天消息；冻结本次选择的 ID/版本 | 设计师确认纳入哪些来源，排除无关或过期内容 |
| 归一与提取 | 按模板字段 key 映射目标、卖点、风格、交付项；图片识别只产出“观察”；聊天抽取保留原话及消息 ID | 核对商品事实和引用；图片识别失败时回退人工录入 |
| 缺口检查 | 检查必填、重复冲突、素材访问、交付规格、版面结构、色板样本数 | 关键规格未核验时只允许生成草稿，不能标记可执行 |
| 方案草拟 | 基于来源快照生成结构化方案；每条结论附证据与分类，输出 1–2 个视觉方向 | 设计师可编辑、删除和补充；编辑记录写明操作者与原因 |
| 确认与冻结 | 对方案版本生成内容哈希，记录确认人、决定与时间 | 按业务策略由品牌方/设计师确认；被退回则新建修订版 |
| 执行与变更 | 将已确认方案版本关联任务、成果、审核；新需求产生新方案版本或显式沿用旧版 | 设计师核对执行基线，不自动覆盖进行中的任务 |

### 放行规则

- **可生成草稿**：有至少一份已提交表单或明确选中的聊天资料；来源可读取；生成服务可用。资料不全时仍生成“待确认项”。
- **可提交方案确认**：正式需求版本已存在；核心目标、交付项、必要素材、硬性约束与交付规格均已核验；冲突已解决；方案每个关键结论能追溯来源或标为设计建议。
- **可执行**：方案已确认，执行任务绑定相同的正式需求版本和方案版本。若业务允许先由设计师作草图，应明确标为“探索草稿”，不能展示为最终交付。

本次截图中的三个限制直接触发关口：`版面结构未接入` → 结构部分待设计师制定；`竞品配色仅 1 色` → 不形成完整色板结论；`交付要求未核验` → 阻止“可执行”状态。

## 5. 与现有系统的衔接

仓库中已实现的基础：

- 管理端有发布版本的表单模板；`ORDER_FORM_PRESETS` 提供 13 类业务表单，包括电商主图、详情页、广告图等。
- 订单协作保存表单实例与提交快照，选择来源生成需求候选版，完成确认后形成不可覆盖的正式需求版本。`RequirementContent.sources` 保留表单字段与答案。
- `GET /api/collaboration/orders/:orderId/requirements/:requirementId/ai-input` 提供正式需求交接数据，并明确 `executionAuthorized: false`；工作流计划只具备契约和修订保存，还没有执行器。
- 售前会话 `POST /api/intake-sessions/:id/summary` 根据最多 200 条消息生成一次性文字总结，前端“协作档案”展示该结果。该结果目前没有结构化证据、方案版本、保存与确认机制。

新增方案服务应复用正式需求的不可变来源快照和现有鉴权/幂等规则。售前会话可先生成“预方案草稿”；转为订单后需重新选择并确认正式需求来源，不能把售前 AI 总结直接升级为执行基线。

### 建议数据模型

| 对象 | 关键字段 | 作用 |
| --- | --- | --- |
| `design_plans` | `id, order_id?, intake_session_id?, requirement_version_id?, current_version_id, status` | 方案身份与上下文；正式方案必须绑定需求版本 |
| `design_plan_versions` | `id, plan_id, version, content_json, content_hash, source_snapshot_hash, mapping_version, model_info_json, created_by, created_at` | 不可覆盖的草稿/审核/确认版本 |
| `design_plan_sources` | `plan_version_id, source_type, source_id, source_version, field_path?, asset_revision?, extraction_status` | 按字段追溯原始证据 |
| `design_plan_decisions` | `plan_version_id, approver_id, decision, comment, acted_at` | 记录确认/退回，确认绑定内容哈希 |
| `design_plan_issues` | `plan_version_id, code, severity, field_path, owner_id?, status, resolution` | 缺项、冲突和核验记录 |

`content_json` 使用服务端 Zod/JSON Schema 校验。至少包含 `summary`、`items[]`、`visualDirections[]`、`copy`、`assets[]`、`deliverables[]`、`openIssues[]`，其中每个重要段落包含 `classification` 与 `sourceRefs[]`。图片资产只保存受控 asset ID/版本，不把签名下载地址或图片二进制放进方案快照。对同一 `(plan_id, version)` 建唯一约束；保存编辑版本使用乐观锁，确认与版本指针更新放在事务中。

### 建议接口（均为待开发）

| 接口 | 用途 |
| --- | --- |
| `POST /api/intake-sessions/:id/design-plans/preview` | 基于选定售前资料生成预方案草稿，保存来源与问题清单 |
| `POST /api/collaboration/orders/:orderId/requirements/:requirementId/design-plans` | 从已确认需求版本创建正式方案草稿；请求包含来源选择和幂等键 |
| `GET /api/design-plans/:id` | 读取方案、版本、来源和待确认项，按项目成员鉴权 |
| `POST /api/design-plans/:id/versions` | 保存设计师修订；带基准版本号，冲突返回 409 |
| `POST /api/design-plans/:id/decisions` | 确认或退回指定内容哈希；写审计记录 |
| `GET /api/design-plans/:id/execution-input` | 仅对已确认版本输出可执行结构；包含需求与方案版本 ID |

图片分析、文案生成和方案草拟应走后端异步任务：请求保存来源快照与任务 ID，Worker 调模型，校验返回结构与引用，再写草稿版本。前端轮询或接收现有实时事件。模型超时/失败时保留来源与问题清单，允许人工编辑；不让模型直接写正式需求或已确认方案。对聊天和附件文本按**数据**处理，忽略其中要求模型改变系统规则的指令。

## 6. 页面与交互

订单协作工作台增加“设计方案”入口：左栏选来源，中栏查看方案章节并编辑，右栏查看每条内容的来源、冲突和待确认项。点击来源可打开对应表单答案、聊天消息或受控图片。顶部始终显示 `需求 vN / 方案 vM / 草稿或已确认`；旧版本可对比，新需求版本出现时提示重新核对。

售前会话“协作档案”保留原始表单和现有总结，将新入口命名为“预方案”。预方案页显示“尚未绑定正式需求”，并提供转订单后重新汇总的路径。移动端先支持阅读、补资料、处理确认；复杂编辑放在 Web 设计师端。

## 7. 分阶段交付与验收

| 阶段 | 范围 | 完成判据 |
| --- | --- | --- |
| M1：可信整理 | 正式需求来源映射、方案固定结构、证据索引、缺口规则、Web 编辑与版本保存 | 同一来源快照可重复生成一致的归一输入；每条关键结论可追溯；冲突和交付未核验不能进入可执行状态 |
| M2：辅助生成 | 图片观察、聊天抽取、AI 方案草稿、1–2 个视觉方向、失败重试 | 模型不能把推断标成已确认要求；竞品单色和未接入版面结构被正确提示；失败可人工继续 |
| M3：确认与执行 | 方案确认、正式版本、任务/成果绑定、需求变更处理；售前预方案转订单衔接 | 任务引用确定的需求与方案版本；旧版可读不可覆盖；退回或改版不篡改历史成果 |

验收样例至少覆盖：多表单同字段冲突、没有商品图、只有一张竞品图、交付规格缺失、聊天要求与表单相反、来源文件不可访问、AI 输出无证据、方案确认后需求升级、重复提交与并发编辑。核心校验使用无外部模型的固定测试资料；模型效果再用人工评审样本验证。

## 8. 本次可直接采用的方案模板

实际项目录入后，可按下面顺序填写：

1. **项目与来源**：订单/会话、选中的表单提交版本、图片资产、聊天范围、正式需求版本。
2. **已确认要求**：设计类型、平台、目标、必展信息、硬性限制、交付项。
3. **证据支持的分析**：商品外观、卖点候选、痛点候选、竞品观察；逐项附来源。
4. **视觉方案 A/B**：每个方向说明主题、构图、色彩、文字层级、所需素材及适用原因。
5. **执行清单**：每张图/每个页面的内容结构、尺寸格式、文案状态、设计责任人。
6. **待确认**：缺失资料、来源冲突、交付核验、图片识别和竞品参考边界。

只有拿到实际填写的表单和图片后，才能把该模板转成某个商品的具体设计方案。
